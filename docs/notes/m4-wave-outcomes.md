## X01 — The mouse-path spike

Full record in [m4-mouse-path.md](m4-mouse-path.md). Four things there need an
owner outside X01's scope.

**Outcome (b), with one hop labelled a hypothesis.** The spike ran headless.
Everything except the last hop was observed: both installed emulators (foot
1.27.0, alacritty 0.17.0) take `?1006h`/`?1000h` and say so over DECRQM, the
terminfo grammar every emulator ships is the grammar `mouse::scan` recognises,
tmux requests exactly those two modes and relays reports byte-identical, and
amx's read path handles them on a real tty. *A wheel turn producing a report*
was not observed: the session is locked (`LockedHint=yes`, `hyprlock`), and a
lock surface takes every pointer event, so the empty result proves nothing. The
note carries a copy-pasteable by-hand procedure (§7) and `wheel-in-emulator.sh`
refuses to run on a locked session rather than producing a false negative.
**X13 does not merge before §7.3's dated heading exists.**

**Hand-off to X03 — 04 §7 and D9's "forwarded unchanged" cannot hold.** A
report's coordinates are viewport-absolute; a pane's application reads them as
pane-local. Observed: tmux rewrote row 20 to row 7 for a pane at `top=13`
(`tmux-relay.py`, `split` scenario). amx's own offsets are never zero even with
a single pane — the content area is the terminal minus a status line
(`crates/amx-client/src/model/mod.rs:364`,
`crates/amx-server/src/actor/core/view.rs:225`) and every pane is inset one
cell for its border (`view.rs:37-45`). So the promise in 04 §7 and the doc
comment at `crates/amx-client/src/input/mouse.rs:5-8` ("forwarded verbatim")
are both false as written, and correcting them is X03's file, not X01's. What
X13 actually does about it is X13's call; the narrow single-pane projection
(X12) is the only case a constant offset covers.

**Hand-off to X03 — 10 §D14 overstates what the wheel exception buys.** DEC
mode `1007` (alternate scroll) is *set by default* in both installed emulators,
observed by DECRQM before amx asked for anything, and amx runs on the alternate
screen. So a wheel turn today already produces cursor-up/cursor-down keys that
the client forwards to the focused pane. The exception buys *unambiguity*, not
*reachability*; 10 §D14's "the concession every trial user reaches for in the
first minute" describes a gap that is partly filled already. One design option
nobody has costed is named in the note (F-3) and left to 10's owner.

**Hand-off to X13 (with a note for X02) — `PaneState.mouse` cannot be a
boolean.** A pane picks an event mode and a report *format* independently
(`vendor/libghostty-vt/src/terminal/mouse.zig:7-13` and `:22-28`), and a pane
that enabled `1000` without `1006` expects the X10 encoding. Forwarding SGR
bytes to it delivers bytes it cannot parse. The field needs the format at
minimum; the honest first cut is to forward only to SGR panes and drop for the
rest, with the drop recorded.

**Note for X13 — restoring a mode you set is not restoring the terminal.** A
client that resets every mode it wrote clears `1007`, which the terminal had
set before amx started, leaving the user's terminal in a state they never
chose. Touch only `1006` and `1000`, in both directions.

**Nothing else diverged.** The scope stayed inside `docs/notes/m4-mouse-path.md`,
`scripts/spike/**` and `crates/amx-client/src/bin/mouse_probe.rs`.

## X03 — Doc truth

**A second stale register row, after DR-17's (R-M4-6).** DR-9's remaining list
names "the R3 correction from the M0 plan (herdr's bindings *are*
bindgen-generated; its defect is the missing regeneration check)" as still open.
It is not: commit `261e33b`, *docs: correct the herdr FFI drift description*
(2026-08-06), rewrote both 04 §3 and 02's W10 to say exactly that, naming the
hand-copied constants (`TERMINAL_DATA_COLOR_FOREGROUND = 18`,
`KITTY_PLACEMENT_DATA_* = 3/10/11`) that sit on top of the generated bindings.
`261e33b` is an ancestor of `b727786`, the tree the register says it re-verified
against — the same shape of miss R-M4-6 records for DR-17, and the second row in
twenty-one that was already paid for. Both halves were re-checked against the
herdr checkout during this task: `herdr/src/ghostty/bindings.rs` opens with
`/* automatically generated by rust-bindgen 0.72.1 */`, and the four constants
are at `herdr/src/ghostty/mod.rs:184,194,195,196`. **X00**: DR-9's R3 clause
should be struck as resolved-before-scheduled, not as work X03 did.

**Scope taken beyond the §5 entry, all inside files X03 already owns.** Three
additions, each named here because none is in the entry's list:

1. **04 §7 and D9's row**, correcting "forwarded … never interpreted" — X01's
   hand-off above assigned this to X03 and the §5 entry predates it. The claim
   was re-verified independently: the content area is the terminal minus a
   status line (`amx-server/src/actor/core/view.rs:224-226`,
   `amx-client/src/model/mod.rs:362-368`) and `inset` takes one cell on every
   side of every pane (`view.rs:40-45`), so a pane is never at the viewport
   origin and a viewport-absolute report cannot be relayed byte-for-byte. 04
   now records the constraint and explicitly leaves the mechanism to
   implementation.
2. **10 §D14's wheel default**, amended to opt-in/off from X01's outcome (b),
   and its "concession every trial user reaches for in the first minute"
   replaced with the `1007` finding — X01's second hand-off. Without this, 03
   and 10 would have disagreed about the same default after X03's 03 edit,
   which is the failure mode the task exists to remove.
3. **04 §10's D14 row**, one clause each for the two amendments, so the decision
   table does not contradict the doc it points at.

**Not taken, and owed to another owner.** `crates/amx-client/src/input/mouse.rs:5-8`
says a report is "forwarded verbatim", which is false for the same reason 04 §7
was. That file is **X07's** in wave 2 and **X13's** in wave 3; X03 does not own
a line in it. Whichever of the two touches the module first should correct the
header, and X13 owns whatever the code then does about the translation.

**One dev-dependency added** (R-M4-13's rule): `bytes` on `amx-client`'s
`[dev-dependencies]`. `GridMessage::encode` is generic over `bytes::BufMut`, so
a test that builds a real grid frame needs the trait in scope; the client itself
never encodes one. `bytes` is already a workspace dependency
(`Cargo.toml:29`) and already compiled for `amx-proto`, so nothing new enters
the dependency tree.

**On tests.** Most of this task is prose and has nothing executable to fail
without it. One claim was made executable: `crates/amx-client/tests/cell_style.rs`
pins the corrected `Attrs` doc comment to the decode, asserting that the wire's
ten style attributes arrive as four plus two colours and that the five dropped
ones are indistinguishable afterwards. It passes on `main` as well — it is a
staleness guard, not a regression test. It was verified to bite by temporarily
giving `Attrs` a `faint` field and mapping it in `stream.rs`, which failed the
suite; the mutation was reverted. **X18** widens exactly this projection and
will have to update the test and the comment in the same change, which is the
point.
