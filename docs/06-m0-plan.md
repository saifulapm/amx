# M0 execution plan

The build plan for **M0 — Skeleton that multiplexes** ([05-roadmap.md](05-roadmap.md)).
Binding design is [04-architecture.md](04-architecture.md); this document does not
change it. Where research contradicted or complicated a decision in 04/05, it is
recorded in [§6 Risks](#6-risks--findings) rather than silently redesigned.

Everything below that states a fact about herdr, libghostty-vt, or a crate was
read from source or from docs.rs during planning. Claims that could not be
verified are marked **unverified** and turned into a spike inside the task that
needs them.

## 1. Decisions taken during research

### D-M0-1 — libghostty-vt: build from vendored Zig source

**Decision:** vendor the libghostty-vt source dist (as herdr does) and build the
static library from source in `amx-vt/build.rs` with a **pinned Zig 0.15.2**.

**Evidence:**

- `herdr/vendor/libghostty-vt.vendor.json` pins source commit
  `c5a21edfcbc2d5b46540ad91b7980aca31f5f1f3`, dist archive
  `libghostty-vt-1.3.2-HEAD-+c5a21edfc.tar.gz`.
- `herdr/scripts/vendor_libghostty_vt.py` produces that tree by running
  `zig build dist -Demit-lib-vt -Doptimize=ReleaseFast` in a clean ghostty
  checkout and extracting the archive; it refuses to vendor from a dirty tree
  and records `source_commit` + `dist_archive` + `extracted_dir`.
- `herdr/build.rs` runs `zig build -Demit-lib-vt -Doptimize=ReleaseFast
  -Dsimd=true -Dtarget=<zig triple> -Dversion-string=<VERSION>
  -Demit-xcframework=false` in the vendored dir at cargo build time and links
  `zig-out/lib/libghostty-vt.a`.
- `herdr/vendor/libghostty-vt/build.zig.zon` declares
  `minimum_zig_version = "0.15.2"`.
- `herdr/.github/workflows/ci.yml` installs **exactly 0.15.2** on every
  platform (`mlugg/setup-zig` with `version: 0.15.2` on Linux/Windows,
  `brew install zig@0.15` on macOS — herdr labels that step "Install patched Zig
  on macOS", so the stock 0.15.2 tarball is apparently not sufficient there).

**Rejected — vendoring a prebuilt `.a`:** it means committing a multi-megabyte
binary per target triple, makes the terminal core unauditable in-tree, breaks
`cargo install` and `cargo build --target` for any triple we did not prebuild,
and is exactly the kind of opaque artifact the "small enough to audit" principle
(03 §7) exists to prevent. We keep an escape hatch instead: if
`AMX_LIBGHOSTTY_VT_LIB_DIR` is set, `build.rs` links the library found there and
skips Zig entirely — that is the path for distro packagers, not for us.

**Two consequences the docs do not mention** (see R1, R2):

1. The local dev machine has Zig **0.16.0**; the vendored tree wants 0.15.2.
   `build.rs` must probe `zig version` and fail with an actionable message
   rather than emitting a Zig compiler error.
2. The vendored tree has **no cached Zig package deps** (no `.zig-cache`, no
   vendored package dir) and `build.zig.zon` declares `uucode` **non-lazily**,
   so the first build fetches from `deps.files.ghostty.org`. herdr solves this
   with a CI cache. T02 must vendor the resolved package set into
   `vendor/zig-packages/` and pass `--system <dir>` (herdr's `build.rs` already
   supports this via `LIBGHOSTTY_VT_ZIG_SYSTEM_DIR`), or, if the package set is
   too large to commit, document the network fetch and cache it in CI.

### D-M0-2 — FFI bindings generated at build time

Per 04 §3, `amx-vt/build.rs` runs `bindgen` over the **vendored headers** into
`OUT_DIR` — the generated file is never committed. The safe wrapper never
re-declares a numeric constant; it maps `sys::GHOSTTY_*` into Rust enums through
exhaustive `match`, so a re-vendor that renames or renumbers anything is a
compile error at the mapping site, and a `#[test]` asserts every wrapper enum
round-trips through its `sys::` constant.

**Correction to the stated motivation (R3):** 04 §3 justifies this as fixing
W10's "hand-copied enum drift". herdr's `src/ghostty/bindings.rs` is in fact
bindgen-generated (`/* automatically generated by rust-bindgen 0.72.1 */`,
4,240 lines) and consumers reference `ffi::GhosttyKey_*` rather than hand-typed
values — I found exactly one hand-written FFI-adjacent constant in herdr
(`KITTY_UNICODE_PLACEHOLDER`), and it is a protocol codepoint, not an enum
value. The real drift risk is different but genuine: the generated file is
**committed with no regeneration or diff check anywhere** in herdr (no `bindgen`
reference in any workflow, justfile, nix file, or doc), so a re-vendor of the
headers does not force the bindings to be regenerated. Build-time generation
removes that failure mode by construction. The decision stands; the rationale in
04 §3 should be corrected by a doc PR.

**Cost:** `bindgen` needs `libclang` at build time. Fallback if that proves too
much contributor friction: commit the generated file **plus** a CI job that
regenerates and diffs — the check herdr lacks. Documented, not chosen.

### D-M0-3 — PTY layer: `rustix` only, no `portable-pty`, no `libc`, no `nix`

**Decision:** amx implements its Unix PTY layer directly on `rustix` 1.1.

**What herdr actually uses portable-pty for on Unix** (`herdr/src/pty/backend/unix.rs`,
94 lines including tests): `openpty` + `spawn_command`, then it immediately
`dup`s the master into an `OwnedFd` and drops the pair. Everything else —
`dup`, `F_SETFD`/`FD_CLOEXEC`, `F_SETFL`/`O_NONBLOCK`, `pipe`, `poll`,
`TIOCSWINSZ` — herdr does through raw `libc` in `herdr/src/pty/fd.rs`.
Both vendored portable-pty patches
(`herdr/vendor/portable-pty.patches.md`) are **Windows-only** (ConPTY DLL
loading; Windows raw command tails). For a Unix-first tool, portable-pty buys
one `openpty` call and costs a vendored crate plus its patch manifest.

**Verified `rustix` 1.1.4 coverage** (docs.rs):

| Need | rustix API | feature |
|---|---|---|
| open pty master | `pty::openpt`, `pty::grantpt`, `pty::unlockpt`, `pty::ptsname` | `pty` (+`alloc` for `ptsname`) |
| controlling tty in child | `process::ioctl_tiocsctty`, `process::setsid` | `process` |
| reap child | `process::waitpid` | `process` |
| poll loop | `event::poll` / `PollFd` | `event` |
| wake pipe | `pipe::pipe_with(CLOEXEC \| NONBLOCK)` | `pipe` |
| resize | `termios::tcsetwinsize` (`Winsize`) | `termios` |
| client raw mode | `termios::tcgetattr`/`tcsetattr`, `Termios::make_raw()` | `termios` |

`rustix::pty` does not expose a combined `openpty`; the four-call sequence is
what the separate `rustix-openpty` crate wraps, and it is ~15 lines. We write
those 15 lines rather than take the dependency. The child is spawned with
`std::process::Command` + `CommandExt::pre_exec` doing `setsid` →
`ioctl_tiocsctty` → `dup2` of the slave onto fds 0/1/2 (this is `login_tty`);
that is the one `unsafe` block in the PTY layer and it carries the invariant
comment CLAUDE.md requires.

**Rejected — `nix`:** it covers the same syscalls but with a coarser feature
model and `libc`-backed calls only; `rustix` has the exact APIs, I/O-safe
`OwnedFd`/`BorrowedFd` types at every boundary (so the fd-ownership bugs herdr
guards against with `duplicate_cloexec_fd` become type errors), and a
`linux_raw` syscall backend that needs no libc at all on Linux.
**Rejected — bare `libc`:** it is what herdr does and it is why `fd.rs` is 241
lines of `unsafe` + `last_os_error()` bookkeeping; `rustix` is that file with
the unsafe removed.

**Kept from herdr's design (mechanism, not code):** one thread per pane owning
the master fd; a `poll()` over `[master, wake_pipe]` with an idle fallback
timeout; a wake pipe written by every handle method after queueing work; a
`response_order` mutex held across the read callback so out-of-band query
replies cannot interleave ahead of in-band ones; non-blocking partial writes
with an offset cursor; `Running`/`Quiesced`/`Released` states so M3's handoff
has somewhere to land.

### D-M0-4 — Client renders with direct ANSI, not ratatui, not crossterm

The client draws exactly three things (04 §3, 03 §2): pane grids blitted from
server-authoritative cells, chrome (borders + one status line), and the picker.

**No `ratatui`:** the pane grid path is "take server cells with their exact SGR
attributes and emit them". `ratatui` requires converting every cell into its own
`Buffer`/`Style` model each frame before it will draw — a per-frame conversion
of every visible cell on the hot path, which the CLAUDE.md performance rule
forbids, in exchange for widgets we use for borders, a status line and a list.
Direct ANSI into a reused `Vec<u8>` with an SGR-state differ is both leaner and
the only way to pass through attributes we do not model.

**No `crossterm`:** we need raw mode (`rustix::termios` + `Termios::make_raw`),
terminal size (`tcgetwinsize`), `SIGWINCH` (`tokio::signal::unix`, already a
dependency), and byte output. crossterm's value is its *event parser*, which
actively works against kitty-keyboard passthrough (05 M0 requires the client
pass kitty-protocol sequences through to the pane rather than decode them into a
lossy `KeyEvent`). The client decodes only enough to recognise the prefix key
and mode keys; everything else is forwarded as bytes.

## 3. Wave 0 — the contracts task

**T01 is one agent, and nothing else starts until it merges.** Its output is a
workspace that compiles, has zero behavior, and pins every type two later
agents would otherwise both invent. Bodies are `todo!()` or trivial; signatures
and doc comments are the deliverable.

Contracts to land, with the shape each must have:

**Ids** (`amx-core/src/id.rs`) — `PaneId`, `WorkspaceId`, `ClientId`,
`SessionId` as `Uuid` newtypes with `Serialize`/`Deserialize`/`Display`/`FromStr`;
`GridGeneration(u64)` monotonic per pane; `ShortNumbers`, the display mapping
from UUID to the user-visible small integer, stable across restarts (herdr's K9
behavior). Constructors are `new_v4`-backed; there is no `from_index`.

**Event bus** (`amx-core/src/event/*`) — per 04 §2:

```rust
pub type Seq = u64;

#[non_exhaustive]
pub enum Event {
    PaneCreated { pane: PaneId, workspace: WorkspaceId },
    PaneExited { pane: PaneId, status: Option<i32> },
    PaneResized { pane: PaneId, rows: u16, cols: u16, generation: GridGeneration },
    PaneDamage { pane: PaneId, generation: GridGeneration },
    PaneRenamed { pane: PaneId, label: String },
    PaneTitle { pane: PaneId, title: String },
    HistoryCommitted { pane: PaneId, range: RowRange },
    HistoryInvalidated { pane: PaneId, from_row: RowId, cause: InvalidationCause },
    HistoryEvicted { pane: PaneId, oldest_row: RowId },
    WorkspaceCreated { workspace: WorkspaceId },
    WorkspaceRenamed { workspace: WorkspaceId, label: String },
    WorkspaceClosed { workspace: WorkspaceId },
    FocusChanged { workspace: WorkspaceId, pane: Option<PaneId> },
    LayoutChanged { workspace: WorkspaceId },
    ClientAttached { client: ClientId },
    ClientDetached { client: ClientId },
}

pub struct Envelope { pub seq: Seq, pub event: Event }
pub enum Delivery { Event(Envelope), Gap { from: Seq, to: Seq } }

impl Bus {
    pub fn new(replay_capacity: usize) -> Self;
    pub fn publish(&self, event: Event) -> Seq;
    pub fn head(&self) -> Seq;
    pub fn subscribe(&self) -> Subscription;            // carries head at subscribe time
    pub fn subscribe_after(&self, seq: Seq) -> Subscription;
}
impl Subscription {
    pub fn subscribed_at(&self) -> Seq;
    pub async fn recv(&mut self) -> Option<Delivery>;   // None only when the bus closes
}
```

The doc comment on `Delivery::Gap` states the contract normatively: a subscriber
that falls behind the replay buffer receives `Gap{from,to}` and never a silent
drop; after a gap the subscriber re-reads state and resumes consuming events
strictly after `to`. `wait.rs` carries `StatePredicate` and the `Waiter` that
implements evaluate-at-subscribe-seq → notify-on-event → re-evaluate-on-gap, so
no transition inside a gap can hang a wait (04 §2).

**Effect** (`amx-core/src/effect.rs`) —

```rust
pub enum Effect { Nothing, PaneDamage(PaneId), Layout, Full }

#[derive(Default)]
pub struct EffectSet { level: Level, panes: Vec<PaneId> }   // Vec is cleared, never freed
impl EffectSet {
    pub fn absorb(&mut self, effect: Effect);
    pub fn drain_into(&mut self, out: &mut Scheduled);      // reuses buffers, no per-frame alloc
    pub fn is_empty(&self) -> bool;
}
```

Ordering is `Nothing < PaneDamage < Layout < Full` on the *level*; the pane list
is only meaningful at `PaneDamage`. Every message handler in `amx-server`
returns `Effect` — the type, not a flag (04 §2, D2).

- **Difficulty:** hard · **Wave:** 2 · **Depends on:** T02

  - `resync_request_emits_a_keyframe`

  - `damage_encode_does_not_allocate_per_frame`
- **Prompt draft:** Implement damage coalescing, keyframes and flow control in
  `amx-server` per `docs/04-architecture.md` §4 — this is protocol v1 behavior,
  not a later optimization, because incremental deltas cannot be dropped without
  corrupting the client grid. Per client and per visible pane keep an
  *accumulated dirty-region set* (rects plus grid generation), not a queue of
  deltas: when the writer is not ready new damage merges into that set, and on
  drain you emit one delta whose cells are read from the current authoritative
  grid at send time. Cross a damage threshold, or receive a resync, or find a
  stale generation, and you send a `grid.reset` keyframe instead. The M0 exit
  criterion includes the adversarial test: a `cat /dev/urandom` pane with a
  stalled client must neither grow server memory unboundedly nor corrupt any
  client's grid — write it so it fails without your change.

### T12 — Scrollback identity and history ranges

- **Difficulty:** hard · **Wave:** 4 · **Depends on:** T08
- **Goal:** monotonic per-pane row ids, the eviction floor, `history.invalidated`,
  and chunked range serving.
- **Scope:** `crates/amx-server/src/history/**`, `crates/amx-vt/src/history.rs`,
  `crates/amx-server/tests/history.rs`.
- **Starts with a spike (R4, R5):** libghostty-vt has no stable row-id concept.
  It does expose `GHOSTTY_TERMINAL_DATA_SCROLLBACK_ROWS` and
  `GHOSTTY_TERMINAL_DATA_TOTAL_ROWS`, and `GHOSTTY_SCROLL_VIEWPORT_ROW` for

  establish, from the headers and from experiment, (a) how to distinguish "rows

  the eviction floor are both correct, and (b) which API reads an arbitrary
  history range *without disturbing the live viewport* — the render state renders
  only the terminal's current viewport, and grid refs are documented as not
  built for render-loop rates. Report the finding before implementing; if
  neither is achievable, say so rather than approximating, because 04 §3's
  cache-invalidation contract depends on it.
- **Acceptance:**
  - `row_ids_are_monotonic_and_never_reused_across_trimming`
  - `row_ids_are_never_reused_across_clear`
  - `width_change_emits_history_invalidated_with_the_right_from_row`
  - `height_change_does_not_emit_history_invalidated` (only width reflows)
  - `eviction_floor_advances_and_ranges_below_it_are_refused_not_faked`
  - `rows_scrolling_out_of_the_live_grid_are_announced_with_id_and_hash`
  - `history_range_is_chunked_and_reassembles_byte_identical`
- **Prompt draft:** Implement amx's scrollback identity model in `amx-server`
  and `amx-vt` per `docs/04-architecture.md` §3: per-pane monotonic row ids

  and on clear, an `oldest_row` eviction floor so clients know what they can no
  longer fetch, and rows leaving the live grid announced on the pane's delta
  stream with id and content hash. Begin with a spike, because libghostty-vt has
  no row-id concept of its own and the exact derivation is the least-verified
  mechanism in M0: establish from the vendored headers and from experiment how
  to tell committed rows from pruned rows, and which API reads an arbitrary
  history range without moving the live viewport. Report what you found before
  you implement, and if the contract in §3 is not achievable as written, say so
  instead of approximating it.

## 6. Risks & findings

Flagged for the orchestrator, not silently resolved.

**R1 — Zig version pin is exact, and the dev machine is wrong.** The vendored
`build.zig.zon` requires `minimum_zig_version = "0.15.2"`; herdr's CI installs
exactly 0.15.2 everywhere, and installs a *homebrew* `zig@0.15` on macOS with a
step literally named "Install patched Zig on macOS", implying the stock 0.15.2
tarball did not work there. This machine has Zig 0.16.0. T02 must establish a
working 0.15.2 first; if 0.16.0 turns out to build the vendored tree cleanly,
that is a better outcome and should be recorded, not assumed.

**R2 — The vendored libghostty-vt build reaches the network.** The vendored
tree has no `.zig-cache` and `build.zig.zon` declares `uucode` **non-lazily**,
so `zig build` fetches from `deps.files.ghostty.org`. herdr handles this with CI
caches only. 05 M0 says "vendor libghostty-vt with herdr-style patch manifests"
and does not budget for vendoring the Zig package set; T02 has it as scope.

**R3 — 04 §3's stated motivation for build-time bindgen is inaccurate.** It
cites W10's "hand-copied enum drift"; herdr's bindings are in fact
bindgen-generated. The real defect is that they are *committed with no
regeneration or diff check anywhere in the repo*, so a re-vendor need not
refresh them. Build-time generation is still the right call — it removes the
failure mode by construction — but 04 §3 and 02's W10 wording should be
corrected by a doc PR. Secondary cost: bindgen requires `libclang` at build
time, which herdr's approach avoids; fallback documented in D-M0-2.

**R4 — libghostty-vt has no row-id concept, so 04 §3's scrollback identity model
is entirely amx-side bookkeeping.** The C API offers `SCROLLBACK_ROWS`,
`TOTAL_ROWS` and absolute viewport addressing (`GHOSTTY_SCROLL_VIEWPORT_ROW`),
but nothing that distinguishes rows *committed* to history from rows *pruned*
off the top — and `RowId` allocation and the eviction floor both depend on that
distinction. **Unverified.** T12 begins with a spike; if the distinction cannot
be derived reliably, the invalidation contract in 04 §3 needs a doc PR before
the client cache is built on it.

**R5 — Reading arbitrary history ranges without moving the live viewport is
unconfirmed.** `ghostty_render_state_update` renders the terminal's *current*
viewport only. Grid refs can traverse the grid but the header states plainly
they are "not meant to be used as the core of a render loop … not built to
sustain the framerates needed". `GHOSTTY_SCROLL_VIEWPORT_ROW` addresses history
rows but mutates the viewport, which other clients and the application see.
**Unverified.** Same spike as R4. If the only path is viewport mutation, chunked
history transfer (04 §4) gets materially more expensive and 05's "scrolls
locally at memory speed" promise depends entirely on the client cache warming
successfully.

**R6 — The pinned libghostty-vt is a non-release commit of an explicitly
unstable API.** `vt.h` opens with "WARNING: This is an incomplete,
work-in-progress API. It is not yet stable and is definitely going to change";
the vendored VERSION is `1.3.2-HEAD-+c5a21edfc`. This matches 05's standing risk
row, but note we would be pinning to the same commit herdr pins to, which is a
commit chosen for herdr's needs, not ours.

**R7 — Grapheme clustering may force a vendored patch on day one.** herdr
carries patch `0001-default-grapheme-cluster-mode` because it "renders terminal
cells directly and requires DEC private mode 2027", and libghostty-vt "exposes
current mode mutation but no C API for configuring terminal default modes" — so
`ESC c` (RIS) turns clustering back off. amx renders cells the same way and hits
the same wall. The cheap path is `ghostty_terminal_mode_set(2027)` at creation
plus re-application whenever a full reset is observed; whether a full reset is
*observable* through the C API is unverified. T02 must answer this. If a patch
is needed we write our own — herdr's is Apache-2.0 and copying it is out of
bounds.

**R8 — 04 §4's derive pipeline is only partly built in M0.** The method table
derives serde names, dispatch and the clap tree in M0; the JSON Schema artifact
has no consumer until `amx api schema` in M4, so it is not built. The plan uses
a `macro_rules!` table rather than a proc-macro crate to avoid adding a seventh
crate outside 05's M0 crate list and a `syn`/`quote` dependency. If a proc-macro
is later wanted, that is a crate-list change and should be a doc PR.

**R9 — The client cluster is the sizing risk.** 05 M0 asks the client for
attach, raw mode, chrome, grid blitting, a local scrollback cache, copy mode,
kitty keyboard passthrough, SGR mouse forwarding, three input modes, BSP layout
operations, and the picker. That is T13–T15 plus T14, four tasks and the only
place in the DAG where three tasks are sequentially chained. If M0 slips, it
slips here. No contradiction with the docs — a scope flag.

**R10 — M0 has no `Persist` and no `AgentHub`.** 04 §2's actor table lists five
actors; M0 builds three (Core, PaneHost, Gateway). The T01 contracts
deliberately do not define persistence or agent messages, so M1/M2 will add
message enums and event variants. `Event` is `#[non_exhaustive]` for exactly
that reason, and the protocol goldens will need updating when those variants
land — expected, but worth knowing before the goldens are treated as frozen.

**R11 — Dropping `portable-pty` is a departure from herdr, not from the docs.**
05 M0 mandates vendoring libghostty-vt and says nothing about portable-pty;
D-M0-3 removes it entirely on the evidence that both of herdr's vendored patches
are Windows-only and Unix usage is one `openpty` call. This also removes a
second patch manifest from the tree. Recording it because it changes what
"herdr-style vendoring" means in practice for amx: one vendored dependency, not
two.
